# Принцип единственной ответственности (SRP)

## Описание

Принцип единственной ответственности (Single Responsibility Principle, SRP) — первый из пяти принципов SOLID, сформулированных Робертом Мартином. Суть принципа: каждый модуль, класс или функция должны иметь одну и только одну причину для изменения. Иначе говоря, программная сущность должна отвечать лишь за одну конкретную задачу в системе.

Нарушение SRP приводит к так называемым «монолитным» классам или модулям — God Object, которые одновременно выполняют бизнес-логику, работают с базой данных, формируют отчёты и взаимодействуют с внешними сервисами. Такой код крайне сложно тестировать, переиспользовать и модифицировать без риска регрессий.

Принцип особенно важен при проектировании АИС, где требования к отдельным аспектам системы (хранение данных, безопасность, бизнес-правила, интерфейс) меняются независимо друг от друга. Следование SRP позволяет изолировать изменения, снижает связанность (coupling) и повышает сцепленность (cohesion) модулей.

## Когда применять

- При проектировании новых классов, сервисов или модулей в любой объектно-ориентированной системе.
- При рефакторинге существующего кода с высокой связанностью.
- Когда одна сущность системы изменяется по нескольким разным причинам (требования UI, требования к БД, бизнес-правила).
- При разработке микросервисов — каждый сервис должен отвечать за один бизнес-домен.
- При проектировании слоёв приложения (Controller, Service, Repository) — каждый слой должен иметь свою зону ответственности.

## Признаки нарушения

- Класс или модуль содержит методы, относящиеся к разным бизнес-доменам (например, `UserService` содержит логику отправки email и работы с базой данных одновременно).
- Одна функция выполняет более одной логически самостоятельной задачи (валидация + сохранение + уведомление в одном методе).
- При изменении одного функционального требования приходится модифицировать класс, отвечающий за другой функционал.
- Класс импортирует зависимости из нескольких несвязанных слоёв (HTTP-клиент, ORM, почтовый клиент — всё в одном месте).
- Тесты для одного метода требуют мокирования множества несвязанных зависимостей.
- В ТЗ описывается один компонент системы, который «отвечает за хранение, обработку и отображение данных».
- Компонент упоминается в разделах с разными бизнес-требованиями без разбиения на подсистемы.
- В ТЗ присутствует формулировка типа «сервис X выполняет следующие функции» с перечислением 10+ разнородных функций.
- Отсутствует разбиение системы на слои (Presentation, Business Logic, Data Access).
- Единый модуль описан как ответственный за аутентификацию, авторизацию, аудит и управление пользователями одновременно.

## Примеры нарушений в ТЗ

- «Модуль управления пользователями отвечает за: регистрацию, аутентификацию, формирование отчётов, отправку уведомлений и хранение логов действий.»
- «Компонент обработки заказов выполняет проверку наличия товара, расчёт стоимости, создание счёта и отправку письма покупателю.»
- «Система должна в рамках одного запроса сохранять данные, валидировать их, логировать операцию и возвращать результат.» (без разделения на слои)
- «Сервис аналитики также обеспечивает управление сессиями пользователей.»

## Рекомендации

- Определите «причины для изменения» каждого компонента — если их больше одной, разбейте компонент.
- Выделяйте отдельные сервисы для: бизнес-логики, доступа к данным, отправки уведомлений, формирования отчётов.
- Используйте слоистую архитектуру (Layered Architecture) или Clean Architecture для явного разделения ответственностей.
- В ТЗ описывайте каждый компонент с одной чётко сформулированной зоной ответственности.
- Применяйте инверсию зависимостей (DIP) для слабого связывания между слоями.
