# Безопасность API (аутентификация, авторизация)

## Описание

Безопасность API является ключевым нефункциональным требованием к любой современной информационной системе. Она охватывает комплекс архитектурных мер по идентификации вызывающей стороны (аутентификация), проверке её полномочий на выполнение запрашиваемой операции над целевым ресурсом (авторизация), защите каналов передачи данных от перехвата и модификации, а также предотвращению злоупотреблений и атак типа «отказ в обслуживании» (DoS/DDoS).

В архитектуре распределённых систем стандартом де-факто является использование протоколов OpenID Connect (OIDC) и OAuth 2.0 с выдачей криптографически подписанных токенов доступа (JSON Web Token — JWT). Для контроля доступа применяются ролевая модель (RBAC — Role-Based Access Control) и модель на основе атрибутов (ABAC — Attribute-Based Access Control).

Архитектура безопасности API также обязательно включает ограничение частоты запросов (Rate Limiting / Throttling), валидацию всех входящих параметров по строгим схемам (защита от SQL/NoSQL Injection, Command Injection), обязательное использование TLS 1.3 с безопасными наборами шифров и применение заголовков безопасности (CORS, CSP, HSTS).

## Когда применять

- Во всех публичных и внутренних API, обеспечивающих доступ к данным или функциям АИС.
- При интеграции мобильных клиентов, сторонних партнёрских систем и веб-интерфейсов.
- В системах, обрабатывающих коммерческую тайну, финансовые транзакции или персональные данные в соответствии с 152-ФЗ.
- При организации межсервисного взаимодействия (Service-to-Service) в архитектуре Zero Trust.

## Признаки нарушения

- Защищённые эндпоинты API доступны без аутентификации или используют постоянные статические токены без срока жизни.
- Отсутствует проверка прав доступа к конкретным объектам (уязвимость BOLA / IDOR — Broken Object Level Authorization).
- Секретные ключи API, пароли и приватные сертификаты захардкожены в исходном коде или хранятся в репозитории.
- Передача авторизационных данных и токенов осуществляется через открытые параметры URL-запроса, а не заголовки Authorization.
- Отсутствует шифрование сетевого трафика (использование HTTP вместо HTTPS/TLS).
- В ТЗ не описана политика формирования и проверки сложности паролей, а также механизмы блокировки при подборе учетных данных.
- Отсутствует ограничение частоты запросов (Rate Limiting) на эндпоинтах входа и сброса пароля.

## Примеры нарушений в ТЗ

- «Эндпоинт получения сведений о клиенте `/api/client/{id}` возвращает данные по переданному идентификатору без валидации прав текущей сессии.»
- «Аутентификация внешних сервисов осуществляется по общему статическому ключу, прописанному в конфигурационном файле.»
- «API личного кабинета функционирует по незащищённому протоколу HTTP для снижения накладных расходов на шифрование.»
- «Требования к ограничению количества попыток ввода пароля и частоте вызовов API не предъявляются.»

## Рекомендации

- Используйте централизованный сервер авторизации (Keycloak, Auth0, IdentityServer) по стандартам OAuth 2.0 / OIDC.
- Применяйте короткоживущие Access Token (срок жизни 5–15 минут) в связке с защищёнными Refresh Token.
- Реализуйте строгую валидацию контекста владения ресурсом на уровне сервисного слоя для защиты от IDOR/BOLA.
- Внедрите централизованный шлюз (API Gateway) с модулями валидации токенов и Rate Limiting на основе алгоритма Token Bucket или Leaky Bucket.
- Храните конфиденциальные данные и секреты в специализированных хранилищах (HashiCorp Vault, AWS Secrets Manager).
