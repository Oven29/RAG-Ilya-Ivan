# Паттерн Saga для распределённых транзакций

## Описание

Saga — паттерн управления распределёнными транзакциями в микросервисных системах. В монолитных приложениях транзакции реализуются через ACID-механизм СУБД. В микросервисах, где каждый сервис имеет собственную базу данных, классические распределённые транзакции (2PC, двухфазный коммит) неприменимы из-за проблем с доступностью и производительностью. Saga решает эту проблему путём разбиения транзакции на последовательность локальных транзакций, каждая из которых публикует событие или сообщение, запускающее следующий шаг.

Существуют две основные реализации Saga. **Choreography (Хореография)**: каждый сервис слушает события, выполняет локальную транзакцию и публикует новое событие — централизованного координатора нет. **Orchestration (Оркестрация)**: выделенный компонент (Saga Orchestrator) последовательно вызывает участников транзакции и управляет потоком. При хореографии система более слабосвязана, при оркестрации — проще для понимания и отладки.

Ключевой концепцией Saga являются **компенсирующие транзакции** (compensating transactions): для каждого шага саги должна быть определена операция отмены. Если шаг N завершается ошибкой, компенсирующие транзакции выполняются в обратном порядке (шаги N-1, N-2, ..., 1). Saga обеспечивает согласованность данных в итоге (eventual consistency), а не немедленную, что требует особого внимания при проектировании бизнес-логики.

## Когда применять

- В микросервисных системах, где бизнес-операция затрагивает несколько сервисов со своими БД.
- Когда необходимо обеспечить согласованность данных без распределённых блокировок (2PC).
- В долго выполняющихся бизнес-процессах (long-running business transactions).
- Когда стоимость отмены операции допустима и компенсирующие транзакции определены.
- В системах с высокими требованиями к доступности, где блокировки недопустимы.

## Признаки нарушения

- Для координации транзакций между сервисами используется двухфазный коммит (2PC), создающий проблемы с доступностью.
- Бизнес-операция, охватывающая несколько сервисов, не имеет определённых компенсирующих транзакций.
- При сбое одного шага многошаговой операции данные остаются в несогласованном состоянии без механизма отката.
- Нет идемпотентности обработчиков событий — повторное получение события вызывает дублирование операции.
- Состояние распределённой транзакции нигде не отслеживается, нет механизма мониторинга «зависших» саг.
- В ТЗ описывается операция, охватывающая несколько сервисов, без механизма обеспечения согласованности.
- В ТЗ не определено поведение системы при частичном сбое многошаговой операции.
- Отсутствует описание компенсирующих операций для бизнес-процессов, охватывающих несколько сервисов.
- В ТЗ применяется термин «транзакция» для операций между разными сервисами без учёта невозможности ACID в распределённой системе.
- Не описаны требования к идемпотентности операций.

## Примеры нарушений в ТЗ

- «Оформление заказа выполняется в единой транзакции: резервирование товара, списание средств и создание заявки на доставку.» (невозможно в микросервисах без Saga)
- «При ошибке оплаты система автоматически откатывает все изменения.» (без описания механизма отката в распределённой среде)
- «Система гарантирует ACID-свойства для операций, охватывающих несколько сервисов.»
- «Механизм компенсирующих транзакций не предусмотрен.»
- «Состояние распределённой операции нигде не сохраняется.»

## Рекомендации

- Определите последовательность шагов саги и соответствующую компенсирующую операцию для каждого шага.
- Выберите реализацию: Choreography (через события) или Orchestration (через Saga Manager).
- Обеспечьте идемпотентность всех обработчиков событий для корректной обработки повторных доставок.
- Храните состояние саги в долговременном хранилище (БД Saga Orchestrator).
- В ТЗ явно описывайте механизм обеспечения согласованности для каждой межсервисной операции.
