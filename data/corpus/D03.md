# Паттерн Репозиторий (Repository Pattern)

## Описание

Паттерн Репозиторий (Repository Pattern) — структурный паттерн проектирования, описывающий уровень абстракции между бизнес-логикой приложения и источником данных (базой данных, файловой системой, внешним API). Репозиторий представляет коллекцию объектов предметной области в памяти и инкапсулирует всю логику доступа к данным, предоставляя бизнес-слою чистый интерфейс, независимый от конкретной СУБД или технологии хранения.

Концепция была популяризирована Эриком Эвансом в книге «Domain-Driven Design» (2003) и Мартином Фаулером в «Patterns of Enterprise Application Architecture» (2002). Основная идея: бизнес-объекты не должны знать о том, как они хранятся — будь то PostgreSQL, MongoDB, Redis или файловая система. Репозиторий скрывает все детали запросов, маппинга и транзакций.

В практике разработки АИС паттерн Репозиторий позволяет легко подменять реализацию хранилища (например, заменить реальную БД на in-memory хранилище для тестов), применять моки при unit-тестировании и соблюдать принцип инверсии зависимостей (DIP). Это делает систему более тестируемой, переносимой и слабосвязанной.

## Когда применять

- В любом приложении с нетривиальной логикой доступа к данным.
- Когда необходимо поддерживать несколько источников данных (основная БД + кэш + внешний API).
- Для обеспечения тестируемости бизнес-логики без реального подключения к базе данных.
- В DDD-архитектурах (Domain-Driven Design) для работы с агрегатами.
- Когда планируется смена СУБД или добавление нового источника данных без изменения бизнес-логики.

## Признаки нарушения

- SQL-запросы или ORM-запросы написаны непосредственно в бизнес-логике (в сервисном слое, в контроллерах).
- Бизнес-логика напрямую импортирует и использует классы ORM (например, `Session`, `Model.query`).
- Один и тот же SQL-запрос дублируется в нескольких местах кодовой базы.
- Нет возможности запустить unit-тесты бизнес-логики без реальной базы данных.
- Смена СУБД требует изменений в сервисном слое или контроллерах.
- В ТЗ не предусмотрен отдельный компонент (слой) для работы с данными — бизнес-логика и хранение описаны в рамках одного модуля.
- В ТЗ описывается прямая зависимость бизнес-сервисов от конкретной СУБД («сервис X напрямую работает с таблицами PostgreSQL»).
- Отсутствует описание интерфейсов доступа к данным в архитектуре системы.
- В ТЗ нет требований к тестируемости слоя данных или к возможности подмены источника данных.
- Архитектурная схема не содержит слоя Data Access / Repository.

## Примеры нарушений в ТЗ

- «Сервис управления заказами напрямую формирует SQL-запросы к базе данных PostgreSQL для получения списка заказов.»
- «Бизнес-логика расчёта стоимости доставки работает с объектами SQLAlchemy Model напрямую.»
- «Компонент аналитики использует те же таблицы БД, что и основной сервис, обращаясь к ним напрямую.»
- «Тестирование бизнес-логики выполняется только в интеграционном режиме с реальной базой данных.»
- «Архитектура системы не предусматривает отдельного слоя доступа к данным.»

## Рекомендации

- Определите интерфейс репозитория в бизнес-слое (`IOrderRepository`) и реализуйте его в слое данных.
- Используйте dependency injection для передачи репозитория в сервисы.
- Создайте отдельные репозитории для каждого агрегата (OrderRepository, UserRepository, ProductRepository).
- Для тестов реализуйте InMemoryRepository, реализующий тот же интерфейс.
- В ТЗ явно выделяйте Data Access Layer как отдельный архитектурный компонент с описанием его интерфейсов.
