# Паттерн Bulkhead и ограничение частоты (Rate Limiting)

## Описание

Паттерн **Bulkhead (Отсеки судна / Переборки)** — архитектурный паттерн отказоустойчивости, заимствованный из судостроения: корпус корабля разделяется герметичными переборками на независимые отсеки, чтобы пробоина в одном отсеке не приводила к затоплению всего судна. В программной инженерии Bulkhead изолирует ресурсы (пулы потоков выполнения, пулы соединений к БД, лимиты памяти), выделенные под разные клиенты, эндпоинты или сервисы.

Если один медленный или сбойный внешний сервис перестает отвечать, запросы к нему исчерпывают только выделенный ему изолированный пул потоков. Остальные функции системы продолжают штатно обрабатываться другими независимыми пулами потоков.

В связке с Bulkhead применяется **Rate Limiting (Ограничение частоты запросов)** — алгоритмический механизм защиты API от перегрузки, DoS-атак и злоупотреблений. Алгоритмы ограничения (Token Bucket, Leaky Bucket, Fixed Window, Sliding Window) лимитируют максимальное число обращений от одного пользователя, IP-адреса или API-ключа за единицу времени, возвращая HTTP-статус `429 Too Many Requests` при превышении.

## Когда применять

- В микросервисных системах при вызове множества разнородных сторонних сервисов с разным SLA.
- В публичных API для защиты бэкенда от всплесков трафика и недобросовестных потребителей.
- В многопоточных сервисах с общими пулами соединений к СУБД.
- В мультитенантных (Multi-tenant) системах для изоляции ресурсов между разными арендаторами.

## Признаки нарушения

- Все исходящие сетевые запросы используют единый общий пул потоков приложения; сбой одного сервиса приводит к исчерпанию потоков и параличу всей системы.
- Отсутствуют ограничения на количество параллельных запросов к медленным интеграционным сервисам.
- В API отсутствуют механизмы Rate Limiting, сервис падает при всплеске запросов от одного некорректно работающего клиента.
- В ТЗ не специфицированы допустимые пределы частоты обращений к публичным эндпоинтам.
- Отсутствует изоляция очередей обработки для задач разного приоритета (критичные платежи и тяжелые аналитические отчеты обрабатываются в одном потоке).

## Примеры нарушений в ТЗ

- «Все входящие HTTP-запросы обрабатываются единым неограниченным пулом потоков веб-сервера.»
- «Ограничение частоты запросов со стороны пользователей и ботов не устанавливается.»
- «Запросы к стороннему ненадежному API внешнего сервиса выполняются в основном потоке обработки пользовательского заказа.»

## Рекомендации

- Выделяйте независимые пулы потоков (Thread Pools) и лимиты семафоров для каждого внешнего зависимого сервиса с помощью библиотек Resilience4j, Polly или настроек Envoy.
- Настройте Rate Limiting на уровне API Gateway с выдачей заголовков `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
- Разделяйте обработку критичных интерактивных запросов пользователей и тяжелых фоновых задач по разным вычислительным узлам или изолированным очередям.
- В ТЗ фиксируйте предельные значения RPS (Requests Per Second) и политики обработки очередей.
