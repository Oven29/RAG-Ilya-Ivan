# ГОСТ 34.602-2020 — Требования к функциям (задачам) системы

## Описание

Раздел «Требования к функциям (задачам), выполняемым системой» (подраздел 4.1.2 ГОСТ 34.602-2020) детализирует функциональное назначение автоматизированной системы. Данный подраздел устанавливает исчерпывающий перечень функций, задач и комплексов задач, подлежащих автоматизации в каждой подсистеме АИС.

Для каждой функции системы в ТЗ должны быть определены:
1. Наименование функции и её краткая характеристика.
2. Временной регламент и периодичность выполнения функции (по событию, по расписанию, непрерывно).
3. Требования к входной информации (источники, форматы данных, периодичность поступления, способы контроля достоверности).
4. Требования к выходной информации (получатели, структура документов, форматы представления, периодичность выдачи).
5. Критерии качества и точности выполнения функции (время отклика, допустимая погрешность расчетов).
6. Действия системы в аварийных ситуациях или при некорректных входных данных.

## Когда применять

- При описании функциональной архитектуры любых информационных, учётных, аналитических и управляющих систем.
- При декомпозиции системы на подсистемы и модули в ТЗ.
- Для формирования методики и программы приёмо-сдаточных испытаний (ПМИ).
- Для формализации требований к интеграционным шлюзам и бизнес-процессам.

## Признаки нарушения

- Функции системы перечислены общим списком без привязки к подсистемам и объектам автоматизации.
- Не указаны форматы входных и выходных данных для автоматизируемых операций.
- Отсутствуют временные характеристики выполнения функций (время реакции, максимальная продолжительность операции).
- В описании функции отсутствуют критерии завершения и ожидаемый результат её выполнения.
- Не специфицировано поведение функции при сбоях, недоступности зависимых модулей или передаче невалидных данных.
- Описание функций подменяется описанием внутренней технической реализации классов и баз данных.

## Примеры нарушений в ТЗ

- «Система должна выполнять функцию формирования отчётов.» (не указаны виды отчётов, входные фильтры, форматы выгрузки и регламент)
- «Модуль производит расчёт скидки для клиента.» (без алгоритма расчёта, входных атрибутов и требований к точности)
- «Время формирования аналитического дашборда не регламентируется.»
- «Обработка ошибок при загрузке реестра не требуется, предполагается, что пользователь вводит корректные данные.»

## Рекомендации

- Структурируйте функциональные требования по подсистемам: Подсистема сбора данных, Подсистема расчёта, Подсистема формирования отчетности.
- Для каждой функции оформляйте паспорта или спецификации Use Case с перечислением предусловий, основного сценария, постусловий и исключений.
- Явно фиксируйте предельно допустимое время выполнения функций (например, «формирование выписки — не более 2 секунд при объёме до 10 000 записей»).
- Определяйте форматы обмена данными (JSON, XML, CSV, XLSX) и протоколы валидации (XSD, JSON Schema).
- Формулируйте функциональные требования языком бизнес-предметной области, избегая привязки к конкретным библиотекам в ТЗ.
