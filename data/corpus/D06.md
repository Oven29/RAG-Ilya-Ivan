# Circuit Breaker в микросервисах

## Описание

Circuit Breaker («автоматический выключатель») — паттерн отказоустойчивости в распределённых системах, предотвращающий каскадное распространение сбоев между микросервисами. Концепция заимствована из электротехники: электрический автомат размыкает цепь при перегрузке, защищая оборудование. В программных системах Circuit Breaker перехватывает вызовы к внешнему сервису и «размыкает цепь» при достижении порога ошибок, немедленно возвращая заглушку (fallback) вместо ожидания таймаута.

Паттерн имеет три состояния. **Closed (Закрыт)** — нормальная работа, все вызовы проходят, статистика ошибок накапливается. **Open (Открыт)** — порог ошибок превышен, все вызовы немедленно отклоняются без обращения к целевому сервису, возвращается fallback-ответ. **Half-Open (Полуоткрыт)** — после таймаута восстановления пропускается ограниченное количество пробных запросов; при успехе автомат закрывается, при неудаче — снова открывается.

Circuit Breaker решает ключевую проблему микросервисных систем: один медленный или недоступный сервис способен «положить» всю систему, исчерпав пул потоков вышестоящих сервисов, которые ждут ответа. Паттерн обеспечивает быстрое завершение вызовов при сбоях (fail fast) и предоставляет время недоступному сервису для восстановления без нарастающей нагрузки.

## Когда применять

- В любой микросервисной архитектуре при наличии синхронных межсервисных вызовов.
- При интеграции с внешними API третьих сторон, которые могут быть недоступны.
- Когда время ответа зависимого сервиса влияет на пользовательский опыт.
- При работе с нестабильными сетевыми соединениями или ненадёжными сервисами.
- В критических цепочках вызовов, где недоступность одного звена может заблокировать весь поток.

## Признаки нарушения

- В архитектуре синхронные вызовы между сервисами выполняются без таймаутов и ограничений числа попыток.
- При сбое одного сервиса весь upstream-сервис зависает, ожидая ответа до истечения TCP-таймаута (сотни секунд).
- Отсутствует fallback-логика: система не определяет, что возвращать клиенту при недоступности зависимости.
- Нет мониторинга состояния Circuit Breaker — команда узнаёт о сбое только от пользователей.
- Повторные попытки (retry) выполняются без экспоненциальной задержки, усугубляя нагрузку на падающий сервис.
- В ТЗ описаны синхронные зависимости между сервисами без упоминания механизмов защиты от сбоев.
- В ТЗ не предусмотрены таймауты на межсервисные вызовы.
- Отсутствует описание поведения системы при недоступности зависимых сервисов (деградированный режим).
- В ТЗ нет требований к реализации Circuit Breaker или аналогичного механизма защиты.
- Схема взаимодействия сервисов не содержит указания на паттерны отказоустойчивости.

## Примеры нарушений в ТЗ

- «Сервис заказов синхронно вызывает сервис инвентаря и ожидает ответа для продолжения обработки.» (без таймаутов и fallback)
- «При недоступности платёжного шлюза система ожидает его восстановления.» (нет Circuit Breaker)
- «Интеграция с внешним API партнёра выполняется синхронно в рамках основного потока обработки запроса.»
- «Система не предусматривает механизмов защиты от каскадных сбоев.»
- «Таймауты на внешние вызовы не установлены, обработка запроса ожидает ответа неограниченное время.»

## Рекомендации

- Используйте библиотеки Circuit Breaker: Hystrix (Java), Resilience4j (Java), Polly (.NET), tenacity (Python).
- Настройте параметры: `failure_threshold` (порог ошибок), `timeout` (таймаут запроса), `recovery_timeout` (время до перехода в Half-Open).
- Определите fallback-поведение для каждого сервиса: кэшированный ответ, пустой список, заглушка.
- Настройте метрики Circuit Breaker для мониторинга (Prometheus + Grafana).
- В ТЗ явно описывайте требования к устойчивости к сбоям внешних зависимостей.
