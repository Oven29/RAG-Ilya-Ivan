# Паттерн Database per Service и изоляция данных

## Описание

Паттерн **Database per Service (Выделенная база данных для каждого сервиса)** — ключевой архитектурный принцип микросервисной архитектуры, требующий, чтобы каждый микросервис владел собственной персистентной базой данных, недоступной напрямую другим микросервисам. Все обращения к данным конкретного сервиса должны производиться исключительно через его публичный программный интерфейс (REST API, gRPC, события).

Использование общей единой базы данных (антипаттерн **Shared Database**) создает скрытую сильную связанность (tight coupling) на уровне схемы данных. Изменение структуры таблицы одним сервисом может незаметно сломать функционал других сервисов. Кроме того, общая база данных становится единой точкой отказа (SPOF) и непреодолимым узким местом производительности при масштабировании.

Паттерн Database per Service также позволяет реализовать концепцию **Polyglot Persistence (Полиглотное хранение данных)**: каждый сервис выбирает СУБД, наилучшим образом подходящую для его характера нагрузки (PostgreSQL для реляционных транзакций, MongoDB для гибких документов, Neo4j для графов, Redis для кэша, ClickHouse для аналитики).

## Когда применять

- Во всех микросервисных архитектурах при масштабировании команды разработки и кодовой базы.
- При необходимости независимого развёртывания, миграции и масштабирования отдельных доменных сервисов.
- В распределенных системах с разными типами обрабатываемых данных.
- Для обеспечения автономии сервисов и локализации отказов БД.

## Признаки нарушения

- Несколько независимых микросервисов подключаются к одной и той же базе данных под одной учетной записью.
- Сервис А читает или модифицирует таблицы, логически принадлежащие домену сервиса Б, в обход API сервиса Б.
- В базе данных присутствуют внешние ключи (Foreign Keys) между таблицами разных доменных сервисов.
- Изменение структуры БД требует одновременного релиза и тестирования нескольких микросервисов.
- В ТЗ описывается разделение системы на микросервисы, но проектируется единая монолитная схема реляционной СУБД.

## Примеры нарушений в ТЗ

- «Все разрабатываемые микросервисы (Биллинг, Каталог, Доставка) работают с единой базой данных Oracle Database и обращаются к общим таблицам.»
- «Сервис формирования аналитики напрямую выполняет выборки SELECT из таблицы заказов сервиса интернет-магазина.»
- «Миграции схемы БД выполняются централизованно администратором раз в месяц с остановкой всех сервисов.»

## Рекомендации

- Закрепите за каждым микросервисом собственную изолированную схему или отдельный инстанс СУБД.
- Категорически запретите прямое сетевое подключение сервисов к чужим хранилищам данных.
- Для чтения связанных данных между сервисами применяйте асинхронную репликацию через события (Event-Driven Data Replication), паттерны API Composition или CQRS.
- В ТЗ фиксируйте границы владения данными (Data Ownership) для каждого компонента системы.
