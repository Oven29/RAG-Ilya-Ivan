# Принцип открытости/закрытости (OCP)

## Описание

Принцип открытости/закрытости (Open/Closed Principle, OCP) — второй принцип SOLID. Сформулирован Бертраном Мейером в 1988 году и переосмыслен Робертом Мартином: программные сущности (классы, модули, функции) должны быть **открыты для расширения**, но **закрыты для модификации**. Это означает, что добавление нового поведения в систему не должно требовать изменения уже написанного и протестированного кода.

На практике OCP достигается через абстракции: интерфейсы, абстрактные классы, стратегии. Вместо того чтобы добавлять новые ветки `if/else` или `switch/case` в существующие методы, новое поведение реализуется в отдельных классах, реализующих общий интерфейс. Система расширяется путём добавления новых реализаций, а не модификации существующих.

OCP тесно связан с паттернами проектирования: Стратегия (Strategy), Декоратор (Decorator), Шаблонный метод (Template Method) — все они являются инструментами реализации этого принципа. В контексте АИС соблюдение OCP критично для долгосрочной поддерживаемости: новые типы документов, новые правила валидации, новые форматы отчётов должны добавляться без правки существующего кода.

## Когда применять

- При проектировании систем с изменчивыми бизнес-правилами (разные типы расчётов, стратегии скидок, варианты экспорта).
- Когда система должна поддерживать плагинную архитектуру или расширения без изменения ядра.
- При разработке библиотек и фреймворков, которые используют сторонние разработчики.
- Когда в коде появляются множественные условные ветвления по типу объекта (`if type == "A" ... elif type == "B"`).
- При проектировании валидаторов, парсеров, экспортёров с разными форматами.

## Признаки нарушения

- В коде присутствуют длинные цепочки `if/elif/else` или `switch/case`, которые проверяют тип объекта и выполняют разные действия.
- При добавлении нового типа объекта (нового формата, нового правила) необходимо модифицировать уже существующий проверенный метод.
- Метод содержит жёстко заданные (`hardcoded`) условия, зависящие от конкретных значений бизнес-логики.
- Отсутствуют интерфейсы или абстрактные классы там, где поведение явно варьируется по типу.
- В ТЗ описывается конкретный перечень типов без механизма расширения («система поддерживает форматы: PDF, DOCX, XLS — и другие форматы добавляться не будут»).
- В ТЗ отсутствует описание механизма добавления новых правил валидации или новых типов обработки без изменения системы.
- Архитектура описана без слоя абстракции между бизнес-логикой и конкретными реализациями.
- Компонент системы жёстко привязан к конкретной СУБД, конкретному почтовому провайдеру, конкретному формату файлов без возможности замены.
- В ТЗ не предусмотрена возможность конфигурирования правил или стратегий без перекомпиляции/перезапуска системы.

## Примеры нарушений в ТЗ

- «Система поддерживает три типа отчётов: PDF, Excel и HTML. Добавление новых форматов не предусмотрено.» (жёсткое закрытие для расширения)
- «Модуль расчёта стоимости содержит специфическую логику для каждого типа клиента, реализованную через условные операторы.»
- «При добавлении нового типа пользователя необходимо внести изменения в модуль аутентификации, модуль авторизации и модуль аудита.»
- «Система интегрируется только с платёжной системой X, замена на другую платёжную систему потребует переработки модуля оплаты.»

## Рекомендации

- Определите «точки вариации» — места, где поведение системы может изменяться, и выразите их через интерфейсы.
- Используйте паттерны Стратегия, Декоратор, Фабричный метод для создания расширяемых компонентов.
- В ТЗ явно указывайте требования к расширяемости: «система должна поддерживать добавление новых типов X без изменения существующего кода».
- Проектируйте плагинные механизмы для изменчивых компонентов (правила валидации, форматы экспорта, стратегии уведомлений).
- Используйте конфигурационные файлы и dependency injection для управления конкретными реализациями.
