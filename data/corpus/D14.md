# Горизонтальное масштабирование и Stateless-архитектура

## Описание

Горизонтальное масштабирование (Scale-Out) — способность информационной системы наращивать свою вычислительную мощность и пропускную способность путём добавления дополнительных независимых узлов (серверов, контейнеров), в отличие от вертикального масштабирования (Scale-Up), ограниченного ресурсами одного физического сервера. Главным архитектурным предусловием эффективного горизонтального масштабирования является принцип отсутствия состояния (Stateless Architecture).

В stateless-архитектуре экземпляры сервиса не сохраняют данные о сессиях, временные файлы или контекст диалога с клиентом в своей локальной памяти между последовательными запросами. Любой запрос от одного и того же клиента может быть успешно обработан любым доступным экземпляром сервиса за балансировщиком нагрузки (Load Balancer: Nginx, HAProxy, Envoy, AWS ALB).

Всё долговременное и сессионное состояние делегируется специализированным внешним распределённым компонентам: СУБД, распределённому кэшу (Redis Cluster), объектным хранилищам (S3/MinIO). На уровне баз данных горизонтальное масштабирование реализуется через шардирование (Sharding), сегментацию данных и создание реплик только для чтения (Read Replicas).

## Когда применять

- В системах с непредсказуемой, сезонной или быстрорастущей нагрузкой.
- При проектировании облачных (Cloud-Native) решений с поддержкой автоматического масштабирования (Kubernetes HPA).
- Для обеспечения высокой доступности: выход из строя одного узла не прерывает обслуживание пользователей.
- При необходимости проводить развёртывание обновлений без остановки сервиса (Zero Downtime Deployment: Rolling Update, Blue-Green, Canary).

## Признаки нарушения

- Сервис сохраняет состояние пользовательской сессии в локальной памяти процесса (in-memory session state) без внешней синхронизации.
- Использование механизма «привязки сессий» (Sticky Sessions / Session Affinity) как обязательного костыля для работы системы.
- Локальная файловая система одного сервера используется для сохранения пользовательских загрузок (аватары, документы).
- Фоновые задачи запускаются по локальному cron внутри контейнера без координации через распределённые блокировки.
- В ТЗ содержится требование наращивать производительность исключительно за счёт закупки серверов с большим объёмом RAM/CPU.
- Приложение не может быть запущено в двух параллельных копиях без конфликтов за доступ к общим ресурсам.

## Примеры нарушений в ТЗ

- «Пользовательская сессия формируется в объекте HttpSession веб-сервера Tomcat и хранится в оперативной памяти данного сервера.»
- «Загружаемые пользователем файлы сканов паспортов сохраняются в локальный каталог `/var/uploads` на сервере приложений.»
- «Масштабирование системы осуществляется путём миграции базы данных на сервер с 128 ядрами процессора.»
- «При падении рабочего экземпляра приложения все авторизованные пользователи принудительно разлогиниваются.»

## Рекомендации

- Проектируйте сервисы приложений как полностью Stateless в соответствии с принципами 12-Factor App (фактор VI — процессы).
- Выносите состояние сессий в распределённое хранилище (Redis) или используйте самодостаточные криптографические токены JWT.
- Все бинарные и мультимедийные файлы передавайте в S3-совместимое объектное хранилище (MinIO, Ceph).
- Настройте балансировщик нагрузки с алгоритмами Round-Robin, Least Connections или IP Hash с постоянным Health Check узлов.
- Используйте контейнеризацию (Docker) и оркестрацию (Kubernetes) с политиками горизонтального автоскейлинга по метрикам нагрузки.
