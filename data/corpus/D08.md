# Event Sourcing

## Описание

Event Sourcing — архитектурный паттерн, при котором состояние приложения хранится не как снимок текущих данных (как в традиционных CRUD-системах), а как последовательность событий, которые привели к этому состоянию. Вместо того чтобы обновлять запись в базе данных («изменить статус заказа на "доставлен"»), система сохраняет событие («OrderDelivered», отметка времени, кто выполнил). Текущее состояние получается путём «воспроизведения» всей цепочки событий с начала.

Event Sourcing обеспечивает полный аудит всех изменений данных — это критически важно для финансовых систем, медицинских записей и любых АИС, где требуется история изменений. Паттерн позволяет «путешествовать во времени»: восстановить состояние объекта на любой момент времени, воспроизвести события для отладки, создать новую проекцию данных ретроактивно. Event Sourcing хорошо сочетается с CQRS и является основой для Event-Driven Architecture.

Основные компоненты: **Event Store** (append-only хранилище событий), **Aggregate** (доменный объект, генерирующий и применяющий события), **Projection/Read Model** (оптимизированное представление для чтения, строящееся из событий), **Snapshot** (периодически сохраняемый снимок состояния для ускорения воспроизведения). Реализации: EventStoreDB, Apache Kafka (как Event Store), Axon Framework.

## Когда применять

- В системах с жёсткими требованиями к аудиту и истории изменений (финансы, медицина, юриспруденция).
- Когда необходима возможность отмены операций (undo/redo) или реиграции событий.
- В сложных доменных моделях с множеством переходов состояний.
- При необходимости построения различных представлений данных из одного источника истины.
- В системах с высокой нагрузкой на запись, где append-only хранилище эффективнее.

## Признаки нарушения

- История изменений данных не сохраняется — система хранит только текущее состояние.
- Аудит реализован как отдельная таблица логов, которую можно изменить или удалить (не является источником истины).
- Операции UPDATE и DELETE применяются к записям без сохранения предыдущего состояния.
- Нет возможности восстановить состояние объекта на произвольный момент времени.
- При ошибке в обработке нет возможности «переиграть» события с исправленной логикой.
- В ТЗ описывается только CRUD-операции (создание, чтение, обновление, удаление) без требований к аудиту изменений.
- В ТЗ требование «журнал изменений» реализовано как дополнительная таблица, а не как основной источник данных.
- Отсутствует требование к неизменяемости (immutability) исторических записей.
- В ТЗ не описан механизм восстановления данных после сбоя из истории событий.
- Требования к аудиту сформулированы расплывчато: «система должна логировать действия пользователей» без указания полноты и неизменяемости.

## Примеры нарушений в ТЗ

- «При изменении данных пользователя система обновляет запись в таблице users.» (без сохранения истории)
- «Журнал аудита хранится в отдельной таблице и может быть очищен администратором.» (нарушение неизменяемости)
- «Система должна хранить текущее состояние всех заказов.» (без требований к истории)
- «Удалённые записи физически удаляются из базы данных.»
- «Отмена операций не предусмотрена — система не поддерживает rollback пользовательских действий.»

## Рекомендации

- Определите список доменных событий для каждого агрегата (`OrderCreated`, `OrderShipped`, `OrderCancelled`).
- Используйте append-only Event Store — события не обновляются и не удаляются.
- Строите Read Model из событий с использованием проекций (Projection).
- Реализуйте снимки (Snapshots) для агрегатов с большой историей событий.
- В ТЗ явно указывайте требования к сохранению полной истории изменений и невозможности их модификации.
