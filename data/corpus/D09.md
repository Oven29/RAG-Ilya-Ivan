# CQRS (Command Query Responsibility Segregation)

## Описание

CQRS (Command Query Responsibility Segregation, Разделение Ответственности Команд и Запросов) — архитектурный паттерн, разделяющий модель чтения данных и модель записи данных в приложении. В традиционных CRUD-системах одна и та же модель используется и для получения, и для изменения данных. CQRS предлагает иметь отдельную модель (Command Model) для операций изменения состояния (create, update, delete) и отдельную модель (Query Model / Read Model) для операций чтения.

Паттерн основан на принципе CQS (Command-Query Separation) Бертрана Мейера: метод либо изменяет состояние (команда, Command), либо возвращает данные (запрос, Query), но никогда одновременно. CQRS расширяет этот принцип до архитектурного уровня, позволяя масштабировать, оптимизировать и даже хранить в разных базах данных сторону чтения и сторону записи независимо друг от друга.

Ключевые преимущества: **масштабируемость** — сторона чтения масштабируется независимо (обычно нагрузка на чтение значительно выше); **оптимизация запросов** — Read Model может быть денормализована, заточена под конкретные запросы, храниться в Elasticsearch или Redis; **упрощение модели** — Write Model содержит только бизнес-правила и валидацию, Read Model оптимизирована для представления. CQRS часто применяется совместно с Event Sourcing.

## Когда применять

- В системах с высокой нагрузкой на чтение, где требуется независимое масштабирование.
- Когда модель для представления данных существенно отличается от модели для их изменения (денормализация, агрегация).
- В сложных доменных моделях, где написание бизнес-правил требует строгой модели.
- Совместно с Event Sourcing для построения материализованных представлений.
- При необходимости разных уровней согласованности (eventual consistency для чтения, strong consistency для записи).

## Признаки нарушения

- Одна и та же модель данных используется и для бизнес-операций, и для формирования отчётов/представлений.
- Запросы на получение данных для отображения нагружают ту же БД, что и операции записи, создавая конкуренцию.
- Сложные аналитические запросы выполняются напрямую к основной транзакционной БД.
- Нет разделения между API endpoints для команд (изменений) и запросов (чтения).
- Read-модели денормализуются прямо в транзакционной базе, создавая избыточность.
- В ТЗ не предусмотрено разделение между операциями чтения и записи при высоких требованиях к производительности чтения.
- В ТЗ описывается единственная база данных без возможности оптимизации под операции чтения.
- Отсутствует описание Read Model и механизма её построения (проекций).
- В ТЗ нет требований к согласованности данных (eventual consistency) при использовании отдельных хранилищ для чтения и записи.
- Аналитика и отчётность в ТЗ описаны как работа с той же СУБД, что и основная бизнес-логика.

## Примеры нарушений в ТЗ

- «Дашборд аналитики выполняет агрегирующие запросы к основной базе данных PostgreSQL.»
- «API системы содержит единый набор endpoints для чтения и записи данных с использованием одной модели.»
- «Высоконагруженные запросы отчётности выполняются в рамках основной транзакционной базы.»
- «Система хранит все данные в одной СУБД без разделения на write-модель и read-модель.»
- «При пиковой нагрузке на чтение производительность записи снижается, так как они используют общий ресурс.»

## Рекомендации

- Определите чёткую границу между Commands (изменяют состояние, возвращают void или ID) и Queries (возвращают данные, не меняют состояние).
- Создайте отдельную Read Model, оптимизированную под конкретные запросы (денормализованные таблицы, Elasticsearch-индекс).
- Обновляйте Read Model асинхронно через события от Write-стороны.
- В ТЗ явно описывайте требования к масштабируемости чтения и допустимый уровень согласованности.
- Начните с логического CQRS (разделение в одной БД) и переходите к физическому при необходимости.
