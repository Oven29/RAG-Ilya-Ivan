# Кэширование в высоконагруженных системах

## Описание

Кэширование — фундаментальный архитектурный паттерн оптимизации производительности, заключающийся во временном сохранении результатов ресурсоёмких операций или часто запрашиваемых данных в быстродействующем промежуточном хранилище (In-Memory Data Grid, Redis, Memcached). Применение кэширования позволяет снизить задержку ответа (latency), защитить нижележащие системы хранения (реляционные СУБД) от пиковых нагрузок и повысить общую пропускную способность АИС.

Существуют различные стратегии кэширования: Cache-Aside (ленивая загрузка по требованию), Write-Through (сквозная синхронная запись в кэш и БД), Write-Behind/Write-Back (асинхронная отложенная запись) и Refresh-Ahead. Критически важными аспектами архитектуры кэширования являются выбор политики вытеснения (LRU, LFU, FIFO), определение времени жизни записей (TTL, Time-To-Live) и стратегия инвалидации данных при их модификации.

Некорректно спроектированное кэширование приводит к серьёзным архитектурным проблемам: эффекту «собачьего хвоста» (Cache Stampede / Thundering Herd), когда при истечении популярного ключа сотни параллельных потоков одновременно обращаются в БД, рассинхронизации данных между кэшем и источником правды, а также исчерпанию оперативной памяти.

## Когда применять

- В системах с высоким отношением операций чтения к операциям записи (Read-Heavy workloads, от 5:1 и выше).
- При выполнении тяжёлых агрегационных или аналитических запросов к базе данных.
- Для хранения сессионных данных пользователей и результатов аутентификации (токены, права доступа).
- В распределённых микросервисных архитектурах для кэширования ответов внешних справочников и сторонних API.
- Для предотвращения деградации времени отклика системы при пиковых всплесках пользовательской активности.

## Признаки нарушения

- Система обращается к реляционной СУБД при каждом запросе на чтение без проверки промежуточного кэша.
- Отсутствует регламент или механизм инвалидации устаревших данных в кэше при операциях модификации (Update, Delete).
- В архитектурном решении не задан TTL (время жизни) для кэшируемых ключей, что приводит к неконтролируемому росту потребления RAM.
- Отсутствует защита от эффекта лавинообразных запросов (Cache Stampede / Dogpiling) с помощью распределённых мьютексов или вероятностного раннего обновления.
- В ТЗ не зафиксированы требования к допустимому уровню консистентности (устареванию) данных при чтении из кэша.
- Кэш используется как единственный источник правды без репликации и долговременного персистентного хранилища.
- В высоконагруженном сервисе применяется локальный in-process кэш при наличии нескольких реплик без механизма синхронизации между ними.

## Примеры нарушений в ТЗ

- «Каждый запрос пользователя на получение каталога товаров выполняет прямой SQL-запрос к таблице товаров в СУБД PostgreSQL.»
- «Система должна хранить данные сессий пользователей в памяти инстанса приложения без использования распределённого кэша.»
- «Кэширование результатов запросов выполняется бессрочно, очистка кэша производится вручную администратором.»
- «При обновлении цен товаров инвалидация кэша каталога не требуется.»

## Рекомендации

- Применяйте паттерн Cache-Aside для чтения редко меняющихся справочных данных.
- Используйте централизованные распределённые in-memory хранилища (Redis Cluster, KeyDB) с настроенной репликацией и политикой maxmemory-policy.
- Всегда устанавливайте явный TTL для всех кэшируемых значений с добавлением случайного джиттера (Jitter) для предотвращения одновременного истечения.
- Реализуйте блокировки (Mutex/Lock) на уровне кэша для предотвращения Cache Stampede при формировании тяжёлых ответов.
- В ТЗ явно специфицируйте допустимое время задержки распространения обновлений (stale data window).
