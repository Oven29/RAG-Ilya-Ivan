# API Gateway паттерн

## Описание

API Gateway — архитектурный паттерн в микросервисных системах, при котором единая точка входа принимает все клиентские запросы и маршрутизирует их к соответствующим внутренним сервисам. Gateway является фасадом для всей системы микросервисов: клиенты (мобильные приложения, веб-интерфейс, партнёрские системы) взаимодействуют только с Gateway, не зная о существовании и адресах внутренних сервисов.

API Gateway выполняет ряд критически важных функций: маршрутизацию запросов к нужному сервису, аутентификацию и авторизацию (JWT-валидация, OAuth2), rate limiting (ограничение числа запросов), SSL-терминацию, агрегацию ответов от нескольких сервисов в один, кэширование, трансформацию запросов/ответов, логирование и трассировку. Вынесение этих cross-cutting concerns в единый компонент исключает их дублирование в каждом сервисе.

Существует несколько вариантов паттерна: **Backend for Frontend (BFF)** — отдельный Gateway для каждого типа клиента (мобильное приложение, веб-приложение) с оптимизированным API; **Gateway Aggregation** — Gateway объединяет несколько запросов к разным сервисам в один ответ; **Gateway Offloading** — Gateway берёт на себя сквозные функции, разгружая бизнес-сервисы. Популярные реализации: Kong, AWS API Gateway, Nginx, Traefik, Envoy.

## Когда применять

- В любой микросервисной архитектуре с несколькими клиентами (мобильные, веб, IoT, партнёры).
- Когда клиентам требуется агрегация данных из нескольких сервисов.
- Для централизованного управления аутентификацией и авторизацией.
- При необходимости rate limiting, мониторинга и трассировки на уровне API.
- При различных требованиях к API у разных типов клиентов (BFF-паттерн).

## Признаки нарушения

- Клиенты знают адреса и API всех внутренних микросервисов и обращаются к ним напрямую.
- Аутентификация и авторизация реализованы по-разному в каждом сервисе независимо.
- Нет единого места для мониторинга входящего трафика — метрики разбросаны по сервисам.
- Клиент вынужден делать несколько последовательных запросов к разным сервисам для одной бизнес-операции.
- SSL-сертификаты и TLS-терминация реализованы индивидуально в каждом сервисе.
- Rate limiting настроен (или не настроен) по-разному в каждом сервисе.
- В ТЗ описывается прямое взаимодействие внешних клиентов со всеми внутренними сервисами по отдельности.
- В ТЗ не предусмотрен единый компонент для управления аутентификацией входящих запросов.
- В архитектурной схеме ТЗ отсутствует API Gateway или его аналог.
- В ТЗ не определены механизмы защиты API (rate limiting, защита от DDoS) на уровне инфраструктуры.
- Каждый сервис в ТЗ описан с собственным публичным адресом и независимой системой аутентификации.

## Примеры нарушений в ТЗ

- «Мобильное приложение обращается к сервису пользователей на порту 8001, к сервису заказов на порту 8002, к сервису оплаты на порту 8003.»
- «Каждый микросервис самостоятельно проверяет JWT-токен входящего запроса.»
- «Клиент последовательно запрашивает данные пользователя, список заказов и историю платежей тремя отдельными запросами.»
- «SSL-сертификат установлен на каждом сервисе отдельно.»
- «Rate limiting не предусмотрен — ограничения на количество запросов отсутствуют.»

## Рекомендации

- Введите единый API Gateway как единственную точку входа для всех внешних клиентов.
- Реализуйте аутентификацию и авторизацию централизованно в Gateway.
- Настройте rate limiting, таймауты и retry на уровне Gateway.
- Для разных типов клиентов рассмотрите BFF (Backend for Frontend) вариант.
- В ТЗ явно описывайте Gateway как архитектурный компонент с его функциями и настройками.
