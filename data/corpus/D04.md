# Паттерн Фасад (Facade Pattern)

## Описание

Паттерн Фасад (Facade Pattern) — структурный паттерн проектирования из каталога «банды четырёх» (Gang of Four). Фасад предоставляет упрощённый интерфейс к сложной подсистеме, набору классов или библиотеке. Клиентский код взаимодействует только с фасадом, не зная о внутреннем устройстве подсистемы — её классах, зависимостях и порядке вызовов.

Ключевая ценность паттерна — снижение сложности взаимодействия с подсистемой. Если для выполнения одной бизнес-операции клиент должен обратиться к 5-7 различным классам в определённом порядке, фасад инкапсулирует эту последовательность в один метод. Это уменьшает связанность между подсистемой и её клиентами, упрощает использование подсистемы и облегчает её замену.

Паттерн широко применяется при разработке API-слоя, при интеграции с внешними сервисами, при построении слоёв приложения. В контексте микросервисной архитектуры роль фасада часто выполняет API Gateway. В АИС фасад помогает скрыть сложность взаимодействия с несколькими внутренними сервисами за единым простым интерфейсом для клиентских приложений.

## Когда применять

- Когда необходимо предоставить простой интерфейс к сложной подсистеме.
- При интеграции с внешними библиотеками или API — фасад изолирует изменения внешнего интерфейса.
- Когда нужно разбить систему на слои и определить точку входа для каждого слоя.
- При необходимости упростить взаимодействие клиентов со сложным набором компонентов.
- В микросервисной архитектуре — для объединения нескольких сервисов под единым endpoint.

## Признаки нарушения

- Клиентский код напрямую обращается к нескольким внутренним классам подсистемы в определённом порядке, дублируя эту логику в разных местах.
- Отсутствует единая точка входа для клиентов, взаимодействующих со сложным модулем.
- При изменении внутренней реализации подсистемы приходится вносить изменения во всех клиентских местах использования.
- Клиентский код содержит низкоуровневые детали работы с подсистемой (инициализация, конфигурация, порядок вызовов).
- Высокая связанность между клиентским кодом и множеством внутренних компонентов подсистемы.
- В ТЗ каждый внешний клиент (мобильное приложение, веб-приложение, партнёрский сервис) описан как взаимодействующий с множеством внутренних API без единого фасадного интерфейса.
- В ТЗ отсутствует описание единого API-шлюза или фасадного сервиса для агрегации вызовов.
- Архитектурная схема в ТЗ показывает прямые соединения клиентов со всеми внутренними сервисами.
- В ТЗ не предусмотрено централизованного места для cross-cutting concerns (логирование, аутентификация, rate limiting).

## Примеры нарушений в ТЗ

- «Мобильное приложение последовательно обращается к сервису пользователей, сервису заказов, сервису платежей и сервису уведомлений для оформления заказа.»
- «Каждый клиент самостоятельно реализует логику агрегации данных из нескольких сервисов.»
- «Веб-приложение и мобильное приложение имеют разные наборы прямых подключений к внутренним микросервисам.»
- «При изменении API внутреннего сервиса необходимо обновить все клиентские приложения.»

## Рекомендации

- Создайте фасадный класс или сервис, инкапсулирующий все взаимодействия с подсистемой.
- В микросервисной архитектуре используйте API Gateway как фасад для внешних клиентов.
- Фасад должен содержать только координирующую логику, не бизнес-логику подсистемы.
- В ТЗ явно описывайте единую точку входа для каждой группы клиентов.
- Документируйте публичный интерфейс фасада — он является контрактом между подсистемой и её клиентами.
