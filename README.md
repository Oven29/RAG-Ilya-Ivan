## 📌 О проекте

**RAG-валидатор архитектурных решений и ТЗ** — это интеллектуальный ассистент для системных аналитиков, архитекторов программного обеспечения и студентов инженерных специальностей.

### Проблема
Ручная проверка технических заданий (ТЗ) и архитектурных описаний на соответствие стандартам (ГОСТ 34.602-2020) и архитектурным паттернам (SOLID, Microservices patterns, Reliability, Observability, Security) отнимает часы рутинного труда и чревата человеческими ошибками. Архитектурные дефекты, пропущенные на этапе ТЗ, стоят в десятки раз дороже при исправлении в продакшене.

### Решение
Пользователь загружает проект ТЗ или описание микросервиса в веб-интерфейс. Система:
1. **Ищет** релевантные статьи базы знаний через **собственную реализацию Okapi BM25** с русской лемматизацией/стеммингом (без сторонних поисковых систем).
2. **Проверяет предметную область**: нерелевантные запросы (ловушки / кулинарные рецепты) отклоняются с вежливым отказом (**Refusal**).
3. **Анализирует архитектуру**: языковая модель (LLM) сопоставляет текст с найденными фрагментами стандартов и выдаёт структурированный отчёт о нарушениях с уровнями критичности (`Critical`, `Major`, `Minor`) и прямыми ссылками на пункты документов.

## 🔬 База знаний (Корпус из 30 документов)

Корпус структурирован по 4 категориям и хранится в `data/corpus/` с реестром в `data/documents.jsonl`:

| ID | Название документа | Категория |
|---|---|---|
| `D01`–`D05` | Принцип единственной ответственности (SRP), Принцип открытости/закрытости (OCP), Репозиторий, Фасад, Наблюдатель | Паттерны проектирования |
| `D06`–`D10` | Circuit Breaker, API Gateway, Event Sourcing, CQRS, Saga для распределённых транзакций | Микросервисы |
| `D11`–`D15` | Кэширование, Мониторинг и логирование, Безопасность API, Горизонтальное масштабирование (Stateless), Отказоустойчивость | Нефункциональные требования |
| `D16`–`D20` | ГОСТ 34.602-2020: Структура ТЗ, Требования к функциям, Требования к видам обеспечения, Интерфейсы, Надежность и RTO/RPO | Стандарты ГОСТ 34 |
| `D21`–`D25` | Принципы LSP & ISP, Инверсия зависимостей (DIP), Transactional Outbox, Bulkhead & Rate Limiting, Database per Service | Архитектурные паттерны |
| `D26`–`D30` | Защита данных (152-ФЗ / ГОСТ Р 34.12), Эргономика UI/UX, Асинхронный обмен и DLQ, 12-Factor App Config, Документирование (C4 / ADR) | Инженерия и надёжность |

Каждый документ содержит обязательные разделы:
* `## Описание`
* `## Когда применять`
* `## Признаки нарушения` *(ключевой раздел для индексации дефектов)*
* `## Примеры нарушений в ТЗ`
* `## Рекомендации`
* `## Источники`

## 📊 Бенчмарк качества (Методика ИУ5 Бауманки)

В соответствии с методическими указаниями НИРС, оценка системы выполняется на фиксированном наборе из **15 вопросов** (`benchmark/questions.jsonl`):
- **10 обычных вопросов** (на каждый вопрос размечено **не менее 3 релевантных документов**).
- **5 вопросов-ловушек** (кулинарные рецепты, погода, анекдоты — проверка корректности отказа `refused=True`).

### Результаты прогона бенчмарка (`python -m benchmark.run --k 5`):

| Метрика | Значение в проекте | Норма кафедры ИУ5 | Статус |
|---|:---:|:---:|:---:|
| **Recall@5** | **1.0000** | $\ge 0.70$ | ✅ **Превзойдено (+30%)** |
| **MRR** (Mean Reciprocal Rank) | **0.9500** | $\ge 0.75$ | ✅ **Превзойдено (+20%)** |
| **CRR** (Correct Rejection Rate) | **1.0000** (5/5) | $= 1.00$ | ✅ **100% отказ на ловушках** |

Все результаты измерений протоколируются в формате JSON в директорию `benchmark/results/`.

## 🚀 Быстрый запуск

### Вариант 1: Запуск через Docker Compose (Рекомендуется)

```bash
# 1. Клонировать репозиторий
git clone https://github.com/RAG-Ilya-Ivan/RAG-Ilya-Ivan.git
cd RAG-Ilya-Ivan

# 2. Создать файл настроек из образца
cp .env.example .env
# При необходимости укажите свой LLM_API_KEY в .env (система работает и в демо-режиме без ключа)

# 3. Собрать и поднять контейнер
docker compose up --build
```
Сервис станет доступен по адресу: **http://localhost:8000**

---

### Вариант 2: Локальный запуск на Python

Требуется **Python 3.11+**.

```bash
# 1. Создать и активировать виртуальное окружение
python -m venv .venv
source .venv/bin/activate       # Linux/macOS
# или: .venv\Scripts\activate   # Windows

# 2. Установить зависимости
pip install -e .

# 3. Запустить сервер разработки
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```
Откройте браузер по адресу: **http://127.0.0.1:8000**

## 🧪 Тестирование и бенчмарк

### Запуск тестов:
```bash
pytest tests/ -v
```
Все 8 тестов покрывают ключевые подсистемы:
* `test_bm25.py` — проверка токенизации, стемминга и корректности ранжирования формулы BM25.
* `test_corpus.py` — целостность всех 30 документов, наличие метаданных и корректность чанкера.
* `test_api.py` — доступность эндпоинтов `/`, `/validate`, обработка пустых запросов и валидация схемы.

### Запуск бенчмарка:
```bash
# Проверка качества поиска (Recall@k, MRR, CRR)
python -m benchmark.run --k 5

# Полная проверка с вызовом LLM (требуется LLM_API_KEY в .env)
python -m benchmark.run --k 5 --llm
```

## 📐 Методология Spec-Driven Development (SDD)

Проект разработан в строгом соответствии с концепцией **Spec-Driven Development**:
1. Все спецификации хранятся в репозитории:
   * `spec/product/product.md` — концепция и границы продукта.
   * `spec/product/scenarios.md` — пользовательские сценарии и крайние случаи.
   * `spec/product/kt1.md` и `spec/product/kt2.md` — критерии приёмки контрольных точек.
   * `spec/tech/architecture.md` — спецификация компонентов и сетевого протокола.
   * `spec/tech/rag.md` — алгоритмическая и математическая спецификация RAG и BM25.
   * `spec/tech/quality.md` — стандарты качества и метрики.
   * `spec/tech/tasks.md` — распределение задач команды.
2. Поведение AI-агентов зафиксировано в файле `AGENTS.md`.
3. История контрольных точек и изменений документируется в `CHANGE_HISTORY.md`.
