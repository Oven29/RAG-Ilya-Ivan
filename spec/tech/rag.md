# Спецификация RAG-движка

## 1. Чанкинг корпуса

### Алгоритм

Каждый Markdown-файл разбивается на чанки по заголовкам второго (`##`) и третьего (`###`) уровня.

```
Файл gost_34_602.md
├── Чанк "Введение"      ← текст до первого ## заголовка
├── Чанк "Общие положения"   ← ## 1. Общие положения
├── Чанк "Назначение системы"  ← ## 2. Назначение ...
│   ├── Чанк "Цели создания"   ← ### 2.1 Цели ...
│   └── Чанк "Задачи"          ← ### 2.2 Задачи ...
└── ...
```

**Правила:**
- Первый блок файла (до первого `##`) получает заголовок `"Введение"`.
- Пустые чанки (только заголовок, нет текста) не индексируются.
- Метаданные чанка: `{"doc": "gost_34_602.md", "section": "Общие положения", "text": "..."}`.

### Реализация (`app/rag/corpus.py`)

```python
@dataclass
class Chunk:
    doc: str        # имя файла
    section: str    # заголовок секции
    text: str       # полный текст секции (включая заголовок)
    tokens: list[str]  # нормализованные токены (после text.py)

def load_corpus(corpus_dir: Path) -> list[Chunk]: ...
def chunk_markdown(doc_name: str, content: str) -> list[Chunk]: ...
```

## 2. Нормализация текста (`app/rag/text.py`)

Пайплайн нормализации применяется **и к корпусу при индексации**, и к запросу пользователя при поиске:

```
Исходный текст
      │
1. lowercase
      │
2. Удаление знаков препинания и цифр
      │
3. Токенизация по пробелам
      │
4. Удаление стоп-слов (русский + английский список)
      │
5. Snowball-стемминг (Russian)   ← библиотека: snowballstemmer
      │
Список нормализованных токенов
```

**Пример:**
```
"Требования к надёжности системы" → ["требован", "надёжн", "систем"]
```

## 3. BM25-индекс (`app/rag/bm25.py`)

### Алгоритм: Okapi BM25

**Параметры:**

| Параметр | Значение | Описание |
|---|---|---|
| `k1` | `1.2` | Коэффициент насыщения частоты термина |
| `b` | `0.75` | Коэффициент нормализации длины документа |

### Формулы

**IDF (Inverse Document Frequency):**

$$\text{IDF}(t) = \ln\left(\frac{N - df(t) + 0.5}{df(t) + 0.5} + 1\right)$$

где:
- $N$ — общее число чанков в корпусе,
- $df(t)$ — число чанков, содержащих термин $t$.

**BM25 score для запроса $Q$ и чанка $d$:**

$$\text{score}(Q, d) = \sum_{t \in Q} \text{IDF}(t) \cdot \frac{tf(t, d) \cdot (k_1 + 1)}{tf(t, d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}$$

где:
- $tf(t, d)$ — частота термина $t$ в чанке $d$,
- $|d|$ — длина чанка (в токенах),
- $\text{avgdl}$ — средняя длина чанка по корпусу.

### Структура индекса

```python

    chunks: list[Chunk]       # все чанки корпуса
    idf: dict[str, float]     # IDF для каждого термина
    avgdl: float              # средняя длина чанка
    
    def score(self, query_tokens: list[str]) -> list[tuple[Chunk, float]]:
```

## 4. Поиск и агрегация (`app/rag/search.py`)

### Top-K поиск

1. Вычислить BM25 score для каждого чанка относительно нормализованного запроса.
2. **Агрегация по документу:** `doc_score = max(chunk_score for chunk in doc_chunks)`.
3. Отсортировать документы по `doc_score` по убыванию.
4. Вернуть top-`k` документов (по умолчанию `k=5`).

### Порог релевантности (Refusal Gate)

```python
TOP_K = 5
RELEVANCE_THRESHOLD = 1.0

results = index.score(query_tokens)
top_docs = aggregate_by_doc(results)[:TOP_K]

if not top_docs or top_docs[0].score < RELEVANCE_THRESHOLD:
    return SearchResult(refused=True, chunks=[])
```

**Семантика порога:** если лучший документ набирает менее 1.0 балла, запрос считается нерелевантным для корпуса.

### Возвращаемая структура

```python
@dataclass
class SearchResult:
    refused: bool
    chunks: list[Chunk]      # top-k релевантных чанков (пустой при refused)
    scores: list[float]      # соответствующие score
```

## 5. Промпт-инжиниринг (`app/api/llm.py`)

### Системный промпт

```
Ты — эксперт по архитектуре программного обеспечения и техническим заданиям.
Анализируй предоставленный текст ТОЛЬКО на основе документов из контекста.
Если текст не относится к архитектуре ПО или техническим заданиям — верни refused: true.
Отвечай СТРОГО в формате JSON, без дополнительного текста.
```

### Пользовательский промпт

```
Контекст (выдержки из базы знаний):
---
{chunk_1_text}
[Источник: {chunk_1_doc}, раздел: {chunk_1_section}]
---
{chunk_2_text}
[Источник: {chunk_2_doc}, раздел: {chunk_2_section}]
---
...

Запрос пользователя:
{query}

Верни JSON строго следующей схемы:
{
  "refused": false,
  "summary": "краткое резюме",
  "violations": [
    {"text": "описание нарушения", "source": "источник", "severity": "high|medium|low"}
  ],
  "sources": ["имя_файла.md"]
}
```

### JSON-схема ответа LLM

```json
{
  "refused": "boolean",
  "summary": "string",
  "violations": [
    {
      "text": "string",
      "source": "string",
      "severity": "high | medium | low"
    }
  ],
  "sources": ["string"]
}
```

**Правила валидации ответа:**
- Если LLM вернула `refused: true`, поля `violations` и `sources` должны быть пустыми массивами.
- Если JSON не парсится — HTTP 500.
- Если схема не валидна (нет обязательных полей) — HTTP 500 с логированием сырого ответа.
