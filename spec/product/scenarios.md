# Сценарии использования

## Основные сценарии (Happy Path)

### Сценарий 1 — Валидация черновика ТЗ

**Актор:** Студент / разработчик  
**Предусловие:** Пользователь написал черновик технического задания.

| Шаг | Действие пользователя | Реакция системы |
|---|---|---|
| 1 | Открывает Web UI | Отображается форма с textarea и кнопкой «Проверить» |
| 2 | Вставляет текст ТЗ в textarea | UI-состояние: **idle** |
| 3 | Нажимает «Проверить» | UI переходит в состояние **loading** (спиннер) |
| 4 | Ожидает (≤ 10 с) | Бэкенд: нормализация → BM25 → промпт → LLM |
| 5 | Получает результат | UI отображает список нарушений с подсветкой и ссылками на источники |

**Ожидаемый выход:**
```json
{
  "refused": false,
  "summary": "Найдено 3 нарушения ТЗ",
  "violations": [
    {
      "text": "Отсутствует раздел «Требования к надёжности»",
      "source": "ГОСТ 34.602-89, раздел 4.5",
      "severity": "high"
    }
  ],
  "sources": ["data/corpus/gost_34_602.md"]
}
```

### Сценарий 2 — Валидация описания архитектуры микросервиса

**Актор:** Junior-разработчик  
**Предусловие:** Разработчик описал архитектуру текстом перед началом реализации.

| Шаг | Действие пользователя | Реакция системы |
|---|---|---|
| 1 | Вводит описание архитектуры (сервисы, взаимодействия) | UI-состояние: **idle** |
| 2 | Нажимает «Проверить» | UI → **loading** |
| 3 | Получает результат | Список замечаний: нет кэширования, нет мониторинга, нет circuit breaker |

**Пример нарушений:**
- «Не описан слой кэширования (Redis/Memcached) — нарушение best practice для read-heavy сервисов» → источник: `microservices_caching.md`
- «Отсутствует упоминание health-check endpoint» → источник: `microservices_observability.md`
- «Нет стратегии retry/circuit breaker для межсервисного взаимодействия» → источник: `resilience_patterns.md`

### Сценарий 3 — Вопрос вне предметной области (Refusal)

**Актор:** Любой пользователь  
**Предусловие:** Пользователь вводит запрос, не связанный с архитектурой ПО или ГОСТами.

| Шаг | Действие пользователя | Реакция системы |
|---|---|---|
| 1 | Вводит «Как приготовить борщ?» | UI → **loading** |
| 2 | Получает отказ | UI отображает состояние **refusal** |

**Ожидаемый выход:**
```json
{
  "refused": true,
  "summary": "Запрос не относится к архитектурным решениям или ТЗ",
  "violations": [],
  "sources": []
}
```

## Граничные случаи (Edge Cases)

### EC-1: Пустой запрос

- **Вход:** textarea пустая или содержит только пробелы.
- **Поведение:** Кнопка «Проверить» неактивна (клиентская валидация) **или** бэкенд возвращает HTTP 422 с описанием ошибки.
- **UI:** Показывается inline-ошибка «Введите текст для проверки».

### EC-2: Очень длинный текст (> 8 000 токенов)

- **Вход:** Пользователь вставляет весь текст диссертации.
- **Поведение:** Бэкенд обрезает входной текст до максимально допустимого размера (конфигурируемый лимит, по умолчанию 4 000 символов) и предупреждает пользователя.
- **UI:** Баннер «Текст обрезан до 4 000 символов. Загрузите документ частями для полной проверки».

### EC-3: Нет релевантных документов в корпусе (BM25 score < 1.0)

- **Вход:** Текст тематически похож на архитектуру, но ни один документ корпуса не набирает достаточный score.
- **Поведение:** Система возвращает `refused: true` с пояснением.
- **UI:** Состояние **refusal** — «Не найдено релевантных источников в базе знаний».

### EC-4: Таймаут LLM

- **Вход:** LLM не отвечает за 30 с.
- **Поведение:** Бэкенд возвращает HTTP 504 и fallback-ответ.
- **UI:** Состояние **error** — «Сервис временно недоступен. Попробуйте позже».

### EC-5: Невалидный JSON от LLM

- **Вход:** LLM вернула текст, не парсящийся в ожидаемую схему.
- **Поведение:** Бэкенд логирует ошибку, возвращает HTTP 500.
- **UI:** Состояние **error** с кнопкой «Повторить».

## UI-состояния

```
         ┌──────────┐
         │   idle   │  ← начальное состояние, форма доступна
         └────┬─────┘
              │ submit
              ▼
         ┌──────────┐
         │ loading  │  ← спиннер, форма заблокирована
         └────┬─────┘
              │
       ┌──────┴──────────────────┐
       ▼                         ▼
 ┌──────────┐             ┌──────────┐
 │  result  │             │  error   │  ← HTTP ошибка / таймаут
 │(нарушения│             └──────────┘
 │  / ok)   │
 └────┬─────┘
      │ refused=true
      ▼
 ┌──────────┐
 │ refusal  │  ← вопрос не по теме / нет источников
 └──────────┘
```

| Состояние | Описание |
|---|---|
| **idle** | Пустая форма, кнопка активна |
| **loading** | Запрос отправлен, ожидание ответа, форма заблокирована |
| **result** | Список нарушений (или «нарушений не найдено»), ссылки на источники |
| **refusal** | Запрос отклонён системой как нерелевантный |
| **error** | Техническая ошибка (LLM недоступен, сервер упал) |
